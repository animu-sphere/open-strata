# v0.23.9 UsdImaging verification

Date: 2026-09-26. Intake: [VRM report 49](https://github.com/animu-sphere/usd-vrm-plugins/blob/main/docs/reports/ost/49-2026-09-26-v0.23.8-no-plugin-kind-for-a-usdimaging-adapter.md).

## Local evidence

The candidate CLI generated a codeless `material-schema` provider and a
`material-adapter` imaging consumer. The existing schema template generates
registered schema name `API` with C++ type name `MaterialSchemaAPI`; the imaging
descriptor and metadata correctly use `usd-imaging:API`.

The selected `lookdev` runtime was an adopted OpenUSD 26.08 install on Windows
x86_64 with Python 3.13. MSVC 19.51 compiled the template and native checker with
the platform's C++20 toolchain. The plugin was discovered through registration
paths, not linked into the checker.

| Check | Result |
| --- | --- |
| Template generation and schema dependency build | PASS |
| Imaging shared library build and target-local installation | PASS |
| L0 metadata and L1 imaging SDK | PASS |
| Native L2 registry lookup and adapter construction | PASS |
| L3 `usdcat` and L4 `Usd.Stage.Open` | PASS |
| Same checks from a package containing its schema provider | PASS |
| Aggregate product with both schema and imaging members | PASS, two exact packages |
| `USDIMAGING_ENABLE_PLUGINS=0` | Expected FAIL, names the setting |
| Nonexistent adapted API schema definition | Expected FAIL, names the missing schema |
| Automated duplicate owners in graph and explicit session | Expected rejection |
| Automated absent imaging SDK / mismatched metadata | Expected rejection |

The first native tests exposed Windows verbatim-path and deep package-path
problems in the new checker build. The final implementation builds in a short,
unique host temporary directory, preserves JSON output, and cleans up its tree.

Workspace tests, clippy with warnings denied, formatting, generated reference
docs and documentation links are release gates. Mocked tests check diagnostics
and dispatch but are not counted as native OpenUSD execution.

## Remaining evidence

This is a generated registration skeleton, not the downstream VRM material
implementation. Re-run `vrmImaging` with the published CLI and repeat native
validation on Linux/macOS. Prim-adapter metadata and dispatch are covered by
automated tests; the native local smoke uses an API-schema adapter. Image output,
scene-index data and invalidation behavior remain the plugin author's tests.
