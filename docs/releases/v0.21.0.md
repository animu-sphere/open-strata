# v0.21.0 - host discovery and dogfooding closure

## Objective

v0.21.0 ships the **discovery** half of DCC host integration — versioned host
records and deterministic Maya and Houdini discovery — together with the
corrective half driven by six v0.20.0 dogfooding passes. Two themes run through
that intake, and they are the same theme at two distances: OpenStrata measured
what a runtime *is* far more carefully than what a runtime *needs*, and the
generated CI contract was narrower than the workspaces it now serves. Running
work inside a host — the headless adapters and the host support matrix — moves
to v0.22.0.

## Completed capabilities

- **DCC host discovery.** The isolated `ost-host` crate owns a versioned
  [host record](../reference/host-discovery.md) — product, version, install root,
  selected executables, Python ABI, platform fingerprint, and discovery evidence
  — plus its status model, a deterministic instance id, and a fingerprint over an
  explicitly versioned input set. `ost host discover | list | inspect` ship on the
  standard envelope and category exit codes. Providers are composable and
  order-stable (explicit path → configured root → vendor environment variable →
  documented install location → opt-in `PATH`), deduplicated by canonical root
  while retaining every provenance. Maya and Houdini validators are read-only,
  bounded, and never interactive, resolving a version metadata-first and
  recording what the answer is worth.
- **A runtime records what a consumer needs, not only what it is.** `runtime
  validate` gained a `consumer-configure` check that configures a trivial
  `find_package(pxr REQUIRED)` against the materialized runtime with the same
  Python Development pins `plugin build` supplies, and `runtime export` re-runs
  the checks so the gate is at publish time. Checks gained a real `skip` state.
  macOS artifacts now carry a measured ABI floor read out of Mach-O load
  commands (`macos-arm64-macos145-py313`), and `runtime pull --build` accepts
  first-class `--sdk` and `--deployment-target` knobs resolved through `xcrun`
  before the spawn.
- **`--build-arg` reaches the components `runtime pull --build` decides.** The
  forced-off component set is applied only when the caller named neither half of
  a pair, and a caller who names both halves is refused before the spawn instead
  of paying a process launch for an `argparse` usage dump. Adopting a tree with
  `--from-usd` now provisions the schema-gen Python dependencies (`jinja2`,
  `MarkupSafe`) the way a `--build` pull already did.
- **A CI cell that is not a bundle.** A cell declares `kind: workspace` and
  builds the workspace CMake tree — the tree that compiles the plain libraries
  and executables the bundle verbs never reach — rendering as its own job with a
  `verify: graph|build|test` ladder. `verify: graph` renders as a separate
  milliseconds-long PR gate. Every bundle-only knob is refused on a workspace
  cell by name.
- **A CI contract that can name a host package.** A source cell declares
  `host_packages` keyed by the runner's native installer (`apt`, `brew`), and the
  generator renders one provisioning step before the build, per-cell gated and
  dispatched on `$RUNNER_OS`.
- **The resolved matrix is readable.** `ost ci matrix [--lane <lane>] [--json]`
  emits the resolved cells — runner, platform/profile/bundle, `up_to`, runtime
  artifact and remote reference, pinned OCI digest, host Python, host packages,
  `kind` — plus the `ost` bootstrap pin, so a hand-written lane consumes the
  matrix instead of duplicating its digest pins.
- **The configure contract is reachable outside `ost plugin build`.** A `plugin
  run` session exports `CMAKE_TOOLCHAIN_FILE` pointing at the same
  `toolchain.cmake` `plugin build` uses, rendering it on demand, so
  `ost plugin run <bundle> -- cmake -S . -B build` configures correctly. A
  toolchain the caller set explicitly wins.
- **The workspace graph gate can be asked for on its own.** `ost plugin test
  --workspace --graph-only` runs the dependency-graph checks and exits on their
  result — no build, no resolved runtime, no packaged artifact.
- **A workspace-built executable can ship in a product.** An
  `openstrata.tool.yaml` member declares a workspace-built executable; `plugin
  package --workspace` packages each into the same dist shape a bundle package
  has, so `--product` composes it with no second code path. `product verify`
  checks it against the tool contract and `product install` places it under
  `tools/<id>/`. A tool package that lost its executable is refused at packaging
  and at verification.
- **`--slim` stops discarding what the build produced.** `share` joins the SDK
  layout, so a slim export keeps the examples and ExecIr reference material
  OpenUSD 26.08 installs there. OpenUSD 26.08's relocated Python bindings
  (`lib/site-packages`, `Lib/site-packages`, versioned
  `lib/python<X.Y>/site-packages`) are discovered, and the concrete directory is
  recorded in the runtime layout.
- **Renderer preset and stall diagnostics.** `configure`/`build` drop managed
  preset includes whose per-target presets file is gone, so `renderer view
  --profile usd` no longer fails on an unrelated absent core preset; a dangling
  include in the user's committed `CMakePresets.json` is reported with the file
  named, never silently rewritten. A managed stall is now a distinct event that
  survives `--quiet` and the JSON stream, naming the active child, phase,
  retained log, remaining timeout budget, and CMake log tails. An interrupted
  `ost` kills the managed process tree it started.

## Compatibility notes

- Host **adapters** are not part of this release. `ost host discover | list |
  inspect` answers which hosts are installed; nothing in v0.21.0 runs a host.
  Adapters, host-standard packaging (Maya `.mod`, Houdini package JSON), and
  support-matrix cells with pinned host evidence move to v0.22.0.
- Host discovery acceptance was exercised on Windows only. The Linux and macOS
  passes move to v0.22.0 with the adapters; those install layouts are encoded
  from documentation rather than demonstrated.
- `PATH` discovery is opt-in by design: an ambient entry describes the calling
  shell, not the machine. `[host.discovery]` roots must be bounded and literal —
  a relative path, a filesystem root, a glob, or anything needing shell expansion
  is refused at parse time.
- `host_packages` is refused on a support lane and on Windows at `ci validate`;
  a Windows runner reached anyway fails the step loudly rather than skipping a
  dependency the configure step needs.
- `--sdk` and `--deployment-target` are refused on a non-macOS host rather than
  silently dropped.
- OpenStrata never installs, updates, licenses, or modifies a host, and no DCC
  API is abstracted.

## Evidence

- Host discovery is covered by unit tests plus fixture-install-tree integration
  tests for both families and a CLI suite for the command contract, all runnable
  on a machine with no DCC installed.
- **Acceptance exercised 2026-07-25 (Windows):** `ost host discover` resolved a
  real Autodesk Maya 2024 and SideFX Houdini 20.5.522 from their default install
  locations, reading both versions from shipped metadata (`MTypes.h`,
  `SYS_Version.h`) and both Python ABIs (cp310, cp311) from the shipped layout.
  `--probe` was exercised against a real `husk.exe` from a root with its metadata
  absent, moving the version from `unknown` to `20.5.522` recorded as
  `source: probe`. The pass corrected three defects the fixtures could not see —
  instance ids carrying the `sha256:` prefix, doubled prefixes in fingerprint
  digests, and mixed path separators in recorded roots and evidence — each now
  covered by a test.
- The corrective half is driven by usd-vrm-plugins reports 28–32 and hdMerlin
  report 10, and covered by lifecycle tests over workspace cells, tool members,
  product verification and installation of a tool, `ci matrix` projection,
  `--graph-only`, the `--build-arg` conflict contract, the macOS ABI-floor
  measurement, and the `consumer-configure` check.

## Known limitations

- OST20-RND-002/003/005 (producer-bound evidence, viewport JSON success
  contract, durable launch record) shipped in v0.20.0 and were exercised locally
  against a real runtime; they remain **unverified downstream** until a managed
  build completes in hdMerlin.
- The declarative half of the consumer-requirements ask is open: a
  `host_requirements` list in the runtime record, renderable into CI and
  checkable at `artifact pull`. v0.21.0 ships the half that lets `ost` *notice*
  and the half that lets a CI contract *say* it, not the half that carries it in
  the record.
