# v0.22.8 - Runtime SDK layout (unreleased)

## Objective

Consume locked compositions through a predictable native SDK prefix, portable
activation, and normal CMake config packages. This describes the working
implementation; the workspace/published version remains v0.22.6. No release tag
is created here, and v0.22.7 publication is still pending.

## Implemented capabilities

- New composition locks include an owner-recorded SDK projection and portable
  Formation environment contributions. Public `bin`, `lib`, `include`, `share`,
  `plugins`, `python`, `node`, and `metadata` roots survive export/reconstruction.
- Producer install mappings expand against the verified inventory. File and
  ancestor collisions, reserved roots, missing sources and ambiguous/uninstalled
  symlink targets fail before publication. Relative symlinks are remapped.
- Component prefixes and producer evidence remain intact. SDK copies are
  independently verified, including modes and symlink bytes. Metadata or owner
  tampering cannot be accepted by merely changing `metadata/sdk.json`.
- `runtime env --composition` emits a verified isolated environment as JSON or
  Bash/PowerShell statements. Shell rendering escapes literal path contents.
- `runtime exec --composition -- <command>` checks host compatibility, resolves
  bare executables on SDK PATH, resets runtime search paths and records process
  results under `--json`. It is not an OS isolation/security sandbox.
- `runtime validate --composition --sdk` checks activation, plugin library and
  resource paths, and schema-resource reachability. Repeatable `--cmake-package`
  explicitly configures installed CMake packages in a fresh restricted prefix.

## Compatibility and evidence boundaries

Legacy locks omit `sdk` and retain their original identity/layout when rebuilt,
exported, or checked with `--locked`. Recompose without `--locked` to opt into
the new identity. Older binaries cannot read SDK-bearing locks.

The SDK preserves declared producer paths and does not patch CMake configs,
plugInfo metadata, RPATH or DLL references. Its extra copies increase artifact
size. Component metadata must provide discovery paths and relocatable installs.

Structural success does not claim native OpenUSD plugin/resolver registration,
schema behavior, device availability or rendering. CMake package probes execute
code only when explicitly requested; their output is separate from immutable
composition evidence. Export validation remains `pending`.

## Verification and remaining gates

- Windows workspace tests and Clippy passed locally.
- A real MSVC/CMake test builds a shared library and installed executable,
  exports the SDK, removes producer build/install trees, reconstructs into a
  separate artifact store, moves the prefix, resolves `find_package(Tiny CONFIG
  REQUIRED)`, builds a separate consumer and runs both executables with SDK
  loader paths. The fixture's plugInfo/schema checks are structural only.
- Regression coverage includes legacy locks, deterministic export/activation,
  empty roots, copy independence, ownership/metadata tampering, missing install
  sources, expanded collisions, and relative symlink remapping.
- Linux/macOS native execution and Unix filesystem symlink/mode CI gates remain
  required. No real OpenUSD/geospatial execution is claimed by the Tiny fixture;
  component-owned plugin/resolver/schema probes remain cross-repository gates.
- Release preparation, version/attribution refresh, CI, merge and publication
  remain separate from this implementation.
