# v0.23.16 — Runtime Python paths in installed library consumers

Fixes [issue #285](https://github.com/animu-sphere/open-strata/issues/285):
`ost library verify-consumer` rejected OpenUSD targets exposing the host Python
development artifacts required by the selected runtime.

## Changes

- Consumer configuration resolves Python with the same runtime-aware resolver
  used by managed library builds and pins its interpreter, include directory and
  library for CMake's `Python3` and `Python` discovery.
- Imported targets may expose that Python include tree, its exact library file,
  and, on Windows, its matching runtime DLL. The library directory is accepted
  as an `INTERFACE_LINK_DIRECTORIES` entry without allowing unrelated files
  beneath it or widening the declared package discovery prefixes.
- `library-consumer.json` records `runtime_python` separately from
  `runtime_prefix` and the library `closure`, including version, source,
  executable, include directory, library and optional runtime DLL. Both successful
  and failed consumer configurations retain this evidence.
- Native CMake fixtures verify Python development discovery and consumer linking,
  and reject unrelated library files, broader include paths and ambient packages.

## Compatibility and limitations

No descriptor changes are required. The report field is additive and is `null`
when matching Python development artifacts cannot be resolved. Missing or
incompatible Python installations gain no path allowance. Python version
selection retains the existing runtime resolver's behavior: the requirement in
the selected OpenUSD package takes precedence over the runtime declaration.

This repair does not establish acceptance for a real downstream package on
every platform. Downstream projects should restore their package contracts and
repeat hosted consumer validation with their locked runtime artifacts.
